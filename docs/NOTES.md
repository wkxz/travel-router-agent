## 需求澄清 2：必吃 ≠ 正餐，要支持特色小吃与夜市

用户指出「必吃」可能是特色小吃而非正餐。设计相应调整为：
- 餐饮双轨：**正餐**（60–90min，每天 2 次占午餐/晚餐）+ **特色小吃**（20–45min，穿插填空档）
  + **夜市/小吃街**（整体当作一个事件占满晚餐时段）
- 行程不再是「2 点 + 2 餐」的机械结构，而是用**时段模板**填充混合序列
- 新增**小吃聚集性**排法：下午景点优先选小吃密集区附近，保证「逛完顺路吃」

### ⚠️ 实测发现（王府井，2026-10-20）：高德没有「小吃」分类码
| types | count | 实际返回 |
|---|---|---|
| 050000 餐饮 | 600 | 全部 |
| 050100 中餐厅 | 439 | 老北京小吃**全在这一档**（卤煮/炸酱面/烤鸭）|
| 050300 快餐 | 54 | 汉堡/呷哺 |
| 050400「小吃快餐」| **8** | **实际是茶饮/咖啡/冰淇淋（休闲餐饮）** |
| 050900「美食城」| **12** | **实际是甜品店** |

→ 分类码语义与直觉不符，**不能靠 types 筛小吃**。
正确做法：`types=050000` + `keywords`（菜系/品类词）+ 对 `poi.type` 字符串做本地二次过滤。
实测 `keywords=小吃` 1.5km 内 397 条，前 5 条即门框胡同百年卤煮、王记爆肚炸酱面等。

这条是「文档/直觉不可信、必须实测」的又一例证（前面还有品牌错字、西厅村屋分类码误解）。

## 需求澄清 3：找「方向不同」的免费 API → 调研结论见 `docs/API-RESEARCH.md`

用户问：除了高德，有没有别的免费接口、方向不同。

### 最大发现（改变了设计方案）
**`extensions=all` 会让高德 POI 返回 `biz_ext`，里面有评分 / 人均 / 营业时间。**
实测王府井 1.5km 小吃 25 条：评分 25/25（100%）、人均 23/25、营业时间 22/25。

→ 「必吃推荐」的排序依据有了（rating + cost + 距离 + 品类），**不需要第三方点评 API**，
  也不需要人工兜底清单。
→ 排程可以做**营业时间可行性校验**（`门框胡同百年卤煮` 营业到 02:00 可排夜宵，
   `陈记卤煮` 20:00 关门就不能排 21:00），之前担心的「推荐了关门的店」能自动挡掉。
→ 代价：响应体变大 2–3 倍，工具层必须精简回传字段，别把原始 JSON 喂给模型。

### 同 Key 的其他高德服务（零成本，已实测）
天气 `/v3/weather/weatherInfo` ✅（要 adcode 不要城市名）、
行政区 `/v3/config/district` ✅（地名→adcode，天气的前置）、
公交 `/v3/direction/transit/integrated` ✅。

### 免 Key 外部接口（已实测）
Open-Meteo ✅（逐小时 + 降水概率，比高德天气细）、OSRM ✅（1392m/120.7s）、
MyMemory ✅（Braised pork intestines → 炖猪肠）。

### 实测不可用（重要，别浪费时间）
`zh.wikipedia.org` / `en.wikipedia.org` / `commons.wikimedia.org` 全部 **000 超时**；
`www.wikidata.org` 一次 200 一次 000，不稳定；LibreTranslate 403；Pexels 401 需 Key。

→ **EdgeOne 部署在腾讯云国内节点，出网环境与本机一致，所以 Wikipedia 系全部不能做生产依赖。**
→ 景点背景讲解改为「交给模型自身知识」，外部数据只负责**实时性信息**（天气/营业时间/距离/评分）。
→ 国内餐饮口碑类 API 现状：大众点评无公开 API、美团/饿了么需企业资质、
   Yelp/Foursquare 国内数据空白。**结论：不要找点评 API，高德自带的已经够。**
