## 1. 一句话定位

**输入「想去的地方 + 想吃的东西 + 玩几天」，输出一份可直接照着走的行程单。**

与参考案例的本质差别：参考案例是「**单点核验**」型 Agent（找一个同时满足 A、B 两个品牌的最近商场），
本项目是「**多目标时空编排**」型 Agent（在 N 天的时间轴上，安排 M 个地点的顺序，并给每一餐配一家餐厅）。

这决定了技术难度的量级完全不同，见第 5 节。

---

## 2. 目标用户与使用场景

| 用户 | 场景 | 输入示例 |
|---|---|---|
| 外地游客 | 第一次去某城市，2~5 天 | 「去成都玩 3 天，想去宽窄巷子和大熊猫基地，必须吃火锅」 |
| 当地大学生 | 周末短途 citywalk | 「南京玩两天，想去博物院，晚上要吃鸭血粉丝汤」 |
| 带家人出行 | 节奏要松、有老人小孩 | 「带爸妈去杭州 2 天，不想太累，想试试本帮菜」 |

共同点：**用户不自己做攻略，只描述意图和约束，Agent 负责全部排布。**

## 3. 能力拆解（四个模块）

### 模块 A：意图解析（关键，决定成败）
从自然语言里抽出结构化约束：

| 字段 | 例子 | 缺失时的处理 |
|---|---|---|
| 目的地城市 | 成都 | 必须追问 |
| 天数 / 夜数 | 3 天 2 夜 | 默认 2 天 1 夜并告知 |
| 必去地点 | 宽窄巷子、大熊猫基地 | 无则按主题推荐 |
| 必吃食物 | 火锅 | 无则按当地特色推荐 |
| 出发地 / 住宿位置 | 住春熙路附近 | 默认市中心 |
| 出行方式 | 公共交通 / 步行 / 打车 | 默认步行为主 |
| 体力偏好 / 忌口 | 不吃辣、老人同行 | 无则不加限制 |
| 预算 | 人均 200 以内 | 无则不约束 |

**关键设计**：缺信息时**分级追问**——只追问「缺了就没法生成」的关键项（城市、天数），
其余用默认值并明确告知用户「我按 X 假设排的，不满意可以改」。

### 模块 B：路线生成（真正的算法部分）
把 M 个必去点排成一条**空间上不折返**的顺序，并切成 N 天，每天控制在合理移动量内。

- 粗排：按经纬度做**贪心最近邻**（从住宿点出发，每次去最近的未访问点）
- 优化：**2-opt** 或**就近交换**，消除交叉
- 切分：按累计移动距离 / 预计耗时切成每天一段，保证单日总车程 ≤ 阈值（如 2 小时）
- 可选：**就近合并 + 空间索引**（高德 place/around 已按距离排序，直接取前 N 个即可）

### 模块 C：必吃推荐（双轨：正餐 + 特色小吃）

用户说的「必吃」其实有两类，节奏和排法完全不同：

| 类型 | 时长 | 举例 | 排法 |
|---|---|---|---|
| **正餐** | 60–90 分钟 | 火锅、烤鸭、日料 | 固定占 午餐/晚餐 时段，每天 2 次 |
| **特色小吃** | 20–45 分钟 | 炸酱面、爆肚、钵钵鸡、冰粉、臭豆腐 | 穿插填空档，可与街区景点合并 |
| **夜市/小吃街** | 1.5–2 小时（整体） | 玉林路、夫子庙、宽窄巷子夜游 | 当成一个「事件」，占用整个晚餐时段 |

**排程含义**：行程不是「每天 2 点 + 2 餐」的机械结构，而是
`景点 → 小吃 → 景点 → 正餐 → 夜市` 的混合序列，用**时段模板**往里填。

#### ⚠️ 实测结论：高德**没有「小吃」这个分类码**

在北京王府井实测各餐饮分类码，结果与直觉不符（2026-10-20 实测）：

| types | count | 实际返回的东西 |
|---|---|---|
| `050000` 餐饮 | 600 | 全部门类 |
| `050100` 中餐厅 | 439 | 卤煮、炸酱面、烤鸭——**老北京小吃全在这里** |
| `050300` 快餐厅 | 54 | 汉堡、呷哺呷哺、肉夹馍 |
| `050400` ~~小吃快餐~~ | **8** | **实际是茶饮/咖啡/冰淇淋（休闲餐饮场所）** |
| `050900` ~~美食城~~ | **12** | **实际是甜品店** |

→ **按分类码筛不出小吃**。地方小吃被归入「中餐厅」下的细分类型
（`餐饮服务;中餐厅;北京菜`、`餐饮服务;中餐厅;中餐厅`）。

**正确筛法**（实测有效）：
1. `types=050000` 取餐饮大类
2. 叠加 `keywords`：菜系词（北京菜、川菜、火锅）或品类词（小吃、特色小吃、老字号）
   → 实测 `keywords=小吃` 在王府井 1.5km 内返回 397 条，前 5 条正是
   门框胡同百年卤煮、王记爆肚炸酱面、老北京炸酱面大王等
3. 再对返回的 `type` 字符串做二次过滤（如排除 `冷饮店`/`甜品店` 若用户没要甜品）

#### 小吃的地理特性：聚集性
小吃不是均匀分布的，而是**扎堆**（老城区、商业街、夜市）。
→ 排程技巧：**下午的景点优先选小吃聚集区附近的**，这样「逛完顺路吃」成立，
   而不是给用户推荐一个要打车 30 分钟才能吃到的「本地小吃」。

#### 必吃的输出要素
店名 · 大致人均 · 距离下一个行程点的步行/车程 · 营业时段匹配 · 一句推荐理由
（老字号 / 本地人常去 / 需排队 / 适合顺路）

### 模块 D：行程编排与输出
- 每天切成 上午 / 午餐 / 下午 / 晚餐 / 夜间，插入通勤时间（用 `/v3/distance` 算真实路线耗时）
- 避开闭馆（17:00 后不要排博物馆）、避开周一闭馆
- **双输出**：① 人读的 Markdown 行程单 ② 机读 JSON（便于后续扩展）

## 4. 工具链设计（可直接复用已验证方案）

| 工具 | 高德接口 | 作用 | 已知坑 |
|---|---|---|---|
| `geocode` | `/v3/geocode/geo` | 地名 → lng,lat | 城市名要给 `city` 参数 |
| `search_around` | `/v3/place/around` | 周边 POI | `types` 是**数字分类码**，且**语义不可靠**（`050400` 不是小吃而是茶饮） |
| `search_text` | `/v3/place/text` | 关键词全局搜 | **周边搜索是严格匹配，关键词错一个字就 0 结果** |
| `filter_by_type` | 本地过滤 | 按 `poi.type` 字符串二次筛选 | 分类码筛不出「小吃」，必须筛 type 字符串 |
| `measure` | `/v3/distance` | 直线(type=0)/驾车(1)/步行(2) | 只有前两种类型特别稳定 |
| `route_estimate` | 多次 `distance` 累加 | 估算各段耗时 | 高频调用，注意 QPS |

**必须沿用的三个实战经验**（来自参考项目踩过的坑）：

1. **QPS 限流**：免费 Key 连发约 50 次触发 `10021`。
   → 必须在 HTTP 层加全局节流（≥0.35s 间隔）+ 退避重试；
   → 且**限流错误必须与「查不到」区分开**，否则会生成「这家店不开/没有」的假结论。
2. **多候选核对**：一条 3 天行程可能要查 15~30 个点，提示词要限制单轮核对数量，分批推进。
3. **关键词纠错**：用户说错店名/地名很常见，工具查不到时应主动提示「你是不是要找 XX」。

## 5. 与参考案例的技术难度对比

| 维度 | 参考案例（找商场） | 本项目（行程编排） |
|---|---|---|
| 工具调用次数 | 9~17 次 | 预计 40~80 次 |
| 是否需要算法 | 否，按距离取最近的就行 | **是**，最近邻 + 2-opt + 时间切分 |
| 输出形态 | 一段 Markdown 文本 | **结构化 itinerary（每天 × 时段 × 地点 × 餐点）** |
| 约束处理 | 单一（二选品牌） | 多重（时间、营业、体力、预算、动线） |
| 失败模式 | 查不到 → 换一个 | **可能产出"看起来合理但根本走不通"的行程** ← 最大风险 |
| 幂等/复算 | 不敏感 | 改一个点要重排整条线 |

**结论**：难点不在「让 Agent 调工具」，而在
**（a）约束表达能力** 和 **（b）结果合法性校验**。
建议把这部分从「全交给 LLM 自由发挥」改成「**LLM 负责语义理解 + Python 负责确定性排程**」。

## 6. 推荐的技术架构

```
用户自然语言
      │
      ▼
[意图解析 Agent]  ── 缺关键信息则追问
      │ 结构化 TripIntent
      ▼
[POI 检索层]  ── 高德 API（带节流/缓存/重试）
      │ 候选集合（景点 + 餐厅）
      ▼
[排程引擎]  ── 纯 Python，确定性算法
      │ 最近邻 → 2-opt → 按天切分 → 插入餐点
      ▼
[校验层]  ── 可达性 / 营业时间 / 时间冲突 / 单日时长
      │ 通过 → 输出；不通过 → 带原因回退重排
      ▼
[渲染层]  ── Markdown 行程单 + JSON
```

关键设计原则：**LLM 不直接写行程表，只输出意图和最终的自然语言解读**，
中间的排程交给确定性代码，避免「幻觉出一条不存在的路线」。

## 7. MVP 范围建议（v1 只做这些）

| 做 | 不做（放到 v2） |
|---|---|
| 单城市、2~4 天 | 多城市联程 |
| 必去点 3~8 个 | 上限 20+ 个点 |
| 每天 2–3 个景点（轻松/均衡/紧凑三档） | 精确到分钟的实时调度 |
| 每天 2 顿正餐 + 2–3 次特色小吃 | 实时排队时长 |
| 小吃按「聚集区就近」排 | 跨城比价、评分榜单 |
| 步行 + 打车两种交通 | 地铁换乘细节 |
| 高德数据 | 票价、用户评价文本 |

**v1 的验收标准**：给 3 个真实城市（北京/成都/南京）+ 3 种天数组合，
生成 9 份行程，人工检查「每一条都走得通」。

## 8. 主要风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 行程「看起来对但走不通」 | 一次性致命（用户白跑一天） | 排程 + 校验必须用代码，不靠 LLM |
| 高德 QPS 限流 | 中途失败、假结论 | 节流 + 重试 + 错误分类 + POI 结果缓存 |
| 关键词严格匹配 | 查不到景点/餐厅 | 查不到时回退到 category 搜索 + 提示用户 |
| 营业时间字段缺失 | 排到闭门的店 | 缺失时保守处理（标注「需现场确认」） |
| 需求发散 | 期末项目做不完 | 严守第 7 节 MVP 边界 |

4. **核心能力**：行程生成 / 必吃推荐 / 智能排布 / 主动追问
5. **技术实现**：架构图 + 工具链 + 算法（最近邻/2-opt）+ 为什么部分交给代码
6. **特色亮点**：不折返路线、营业时间校验、查不到会主动纠错、限流不糊弄
7. **已验证效果**：真实城市跑出的样例行程
8. **后续规划**：v2 功能、接入更多数据源
