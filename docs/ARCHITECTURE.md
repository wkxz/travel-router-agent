# 架构与设计

## 设计原则

**LLM 只做意图理解、检索与解读；行程表由确定性 Python 排程引擎生成，并经独立校验器复核。**

让大模型直接写行程，必然产出「看起来合理但根本走不通」的结果：景点闭馆时安排参观、饭点排在 40 分钟车程外、
返程日赶不上车。这是这类应用最大的风险。因此：

- 模型只能引用工具返回的 **POI id**，接触不到坐标、评分、营业时间，无法编造或改写这些事实；
- 时间、路程、营业时段全部由引擎计算，排程结果交给校验器复核，**有错误就拒绝输出**；
- 行程卡片由 SSE `plan` 事件直接推给前端渲染，不经模型转述。

模型自身的地方经验（要不要预约、门票、从哪个站进、最佳时段）同样有价值，通用大模型写的攻略「实用」主要靠这部分。
所以允许模型给每个景点附一句 `tips`：压成一行、截断到 120 字后**原样**显示在卡片对应景点下，并标明「经验建议，未经核实」。
它只是附注，不参与排程，也不能写营业时间（以检索数据为准）。

## 请求链路

```
浏览器  POST /chat {message, userId}，请求头 X-Conversation-Id
  → server/app.py             保存用户消息、登记取消信号，返回 SSE 流
  → app/agent.py              chat_events()：Agent 定义、提示词（每次请求注入北京时间当天日期）
  → OpenAI Agents SDK         Runner.run_streamed，模型决定调用哪些工具（可并行）
  → app/_tools.py             5 个工具
  → app/_data/                高德客户端、POI 仓库（按会话缓存）、路网通勤、工具参数 → 引擎输入
  → app/engine/               分天 → 时间轴 → 校验 → 渲染
  ← SSE：text_delta（回复文字）/ tool_called（工具指示灯）/ plan（行程卡片）/ error / done
  → server/app.py             流结束（含停止、断开）时把回复文字与行程保存为助手消息
```

`app/` 与 Web 框架无关：`chat_events(message, conversation_id, session, cancel_event)` 只产出 SSE 文本帧，
会话记忆和取消信号由调用方传入。`server/` 负责 HTTP、存储和取消；`eval/` 直接在进程内调用 `chat_events`。

## HTTP 接口 `server/app.py`

Starlette + uvicorn，单进程。除 `/health` 和前端外均为 `POST` + JSON。

| 路由 | 请求体 | 返回 |
|---|---|---|
| `/chat` | `{message, userId?, userMsgId?, botMsgId?}`，请求头 `X-Conversation-Id`（缺省时新建） | `text/event-stream`；带 `X-Accel-Buffering: no` 关闭代理缓冲 |
| `/chat/stop` | `{conversation_id}` | `{status, conversationId, aborted}`：置位该会话的取消信号 |
| `/conversations` | `{user_id, limit?, order?, after?}` | `{conversations, nextCursor}`，按最近消息排序，`after` 为偏移量游标 |
| `/history` | `{conversation_id}` | `{messages}`，助手消息带 `plan`，刷新后能恢复行程卡片 |
| `/clear-history` | `{conversation_id}` | 清空聊天记录与模型记忆，保留会话 |
| `/delete-conversation` | `{conversation_id}` | 删除会话、聊天记录与模型记忆 |
| `GET /health` | — | `{status: ok \| misconfigured, missing: [变量名]}` |
| 其余 `GET` | — | `dist/` 下的前端文件；找不到时回退 `index.html`（单页应用）；路径限制在 `dist/` 内 |

停止生成：`/chat` 为每个进行中的会话登记一个 `asyncio.Event`，`/chat/stop` 置位后 `chat_events` 取消当前运行，
已生成的部分照常保存。取消必须调用 `RunResultStreaming.cancel()`：只是不再读事件流的话，SDK 的后台任务会继续调模型和工具
（实测停止后 3 秒内又调了 6 次工具，`tests/test_stop_run.py`）。因为信号在进程内存里，**服务只能单进程运行**。

## 存储 `server/store.py`

一个 SQLite 文件（WAL 模式），标准库 `sqlite3` 实现：

| 表 | 维护方 | 内容 |
|---|---|---|
| `conversations` | `Store` | id、user_id、标题（第一条用户消息前 8 字）、预览（去 Markdown 符号）、创建与最近消息时间 |
| `messages` | `Store` | 每轮一条用户消息、一条助手消息；助手消息的 `plan` 列存行程 JSON |
| `agent_sessions` / `agent_messages` | OpenAI Agents SDK `SQLiteSession` | 模型多轮记忆（含上一轮工具结果），按会话 id 隔离 |

界面看到的聊天记录与模型的记忆分开存：前者只有文字与行程卡片，后者是 SDK 需要的完整消息条目。
删除、清空会话时两边一起删。用户用浏览器 `localStorage` 里的随机 id 区分，没有登录鉴权。

## 工具

| 工具 | 高德接口 | 作用 |
|---|---|---|
| `geocode_location` | `/v3/geocode/geo` | 酒店、车站、地标 → 坐标与 id |
| `get_city_weather` | `/v3/config/district` + `/v3/weather/weatherInfo` | 未来几天天气（天气接口要 adcode，先查行政区） |
| `search_scenic_spots` | `/v3/place/text` / `around` | 景点检索，可限定在某地点 15km 内；按景点类目搜不到名字对得上的（如书店、老字号）时不限类目再搜一次 |
| `search_food_and_snacks` | 同上，`extensions=all` | 餐饮检索（正餐 / 特色小吃 / 夜市），可限定在某景点 4km 内；带评分、人均、营业时间 |
| `generate_trip_itinerary` | `/v3/distance`（路网） | 调用排程引擎，返回精简行程 `itinerary` + `plan_no` + `gaps`（缺口清单）+ `next_step`（下一步建议） |

工具层约定：

- 只回传模型需要的少量字段（高德单条 POI 有 40 多个字段，全传会撑爆上下文）。
- 排程工具给模型的是精简行程（`_tools.plan_view`：每项只有「时间 + 标题 + 提醒」，加上未安排、未满足的必吃、费用）；
  完整行程（坐标、营业时间原文、交通、描述）存进本轮 `TripContext.plans`，工具输出只带编号 `plan_no`，
  `agent.py` 按编号取出推 `plan` 事件。第 5 轮测评的 16 次排程，返回给模型的内容平均从 7193 字符降到 1099 字符；
  会话记忆会保存工具输出，多轮对话时省下的部分每轮都不再重发。
- 失败返回具体原因（`{"error": ...}`），绝不当成空结果；错误文本先脱敏，Key 不会出现在任何返回给模型的文本里。
- 必填参数在函数内自检并点名缺了哪个，避免 SDK 默认只给出笼统的 "An error occurred"。
- 排程结果有缺口（必吃没排上、饭点只能「周边自选」）时，`gaps` 给出缺口位置，`next_step` 告诉模型在哪里补检索、只重排一次；
  没有缺口时明确告诉模型不要重排、不要自行删减景点。

## 数据层 `app/_data/`

| 模块 | 职责 |
|---|---|
| `amap.py` | 高德请求统一入口：注入 Key、全局节流（最小间隔 0.35 秒）、QPS 超限（10019~10022）退避重试、`status` 校验、错误脱敏；额度用完（实测 10044，免费额度按月算）时熔断 10 分钟，期间不发请求、直接告诉模型「额度已用完，不要换关键词重试」，之后放一个请求探测，恢复后自动继续 |
| `poi_repo.py` | 按会话缓存检索到的 POI，模型后续只需引用 id；为风景名胜类景点补查门区（见下文「大型景区门区」） |
| `routing.py` | `AmapTravel`：按终点批量请求 `/v3/distance`（起点每批不超过 100 个，超出部分高德会静默丢弃），步行/驾车路网时长；取不到时回退直线估算并标注「估算」；识别隔水绕行 |
| `trip_input.py` | 工具参数（id 列表、点名、指定日期、忌口、预算）→ 引擎的 `Spot` / `Restaurant`；匹配必吃菜名；过滤忌口与超预算餐厅（忌口含「辣」时按常见辣味菜名补全：凉粉、冒烤鸭、钵钵鸡等，店名里常常不带「辣」字） |

## 排程引擎 `app/engine/`

纯 Python、不访问网络，可脱离 Agent 单独测试。

| 模块 | 职责 |
|---|---|
| `models.py` | 数据结构：`Spot`、`Restaurant`、`ScheduleItem`、`DayItinerary`、`FullTripPlan` |
| `calendar_pack.py` | 分天：景点 ≤12 个时状态压缩 DP 穷举所有分法，当天顺序穷举全排列（每天至多 4 个景点）；更多时用空间聚类 + 装箱启发式 |
| `optimizer.py` | 启发式分天时的当天顺序：最近邻 + 2-opt 消除折返 |
| `timeline.py` | 时间线模拟：分天阶段判断某天按营业时段走不走得通 |
| `scheduler.py` | 逐天排出时间轴：景点、三餐、小吃、空档、回住处休整、返程赶车 |
| `hours.py` | 按日期取营业时间：星期条款（列表项可以是区间，如「周一，周三至周日」）、节假日特殊日期、不写年份的季节段（可跨年，含「10月1日-10月6日」短横线、「次年」、几段用「与」共用一段时刻、时刻在前日期段在后的括号「06:30-18:30（2月1日-11月30日）」）、全天关闭、只写「营业」不带时刻、「次日」跨零点；节假日注释（「（含周一）」、以「节假日」开头的分句）不当平日时间；`calendar_pack.parse_closed_days` 直接用同一判定，两边口径一致 |
| `geo.py` | 球面距离、通勤估算、营业窗口判断 |
| `travel.py` | `TravelTimes` 接口：默认按直线估算；真实路网由数据层子类注入 |
| `validator.py` | 独立复核：时间重叠、通勤是否够、营业时间、闭馆、餐厅与必吃重复、到站缓冲；有 error 即拒绝输出 |
| `renderer.py` | 行程 → 前端用的字典 / Markdown，生成出行提示 |

### 分天

目标依次是：**排进去的景点最多**（用户点名的景点舍弃代价远高于模型补充的景点，放不下时先舍弃后者）→ **通勤最短** → **每天负荷均衡**（负荷平方和）。
通勤与均衡之外还有两项代价：

- **同片区不拆开**：门区间距 ≤1.2km（步行可达）的两个景点分到不同天，每对计 60（约合 1 小时通勤）。
  南京实测老门东与夫子庙（1.07km）、中山陵与音乐台（0.91km）曾被拆到两天，第二天又专程打车回同一片区；
- **宜傍晚改白天**：宜傍晚的景点当天只能白天去（返程日，或当晚夜游已排满）时计 90；
  但和当晚的夜游景点步行可达时不计——一个下午逛、一个晚上逛正是同片区的合理安排。

这两项都排在「排进去的景点最多」之后：时间放不下时宁可拆开也不丢景点。

**子景点**：名称里含另一个所选景点的名称（去掉「景区」等后缀与括号里的分店名）、且相距 ≤1.5km 的（取 3km 时「西湖文化广场」这类只是名字带景区名的地点也会被认进来），视为该景区里的一个点
（`calendar_pack.is_sub_spot`）。模型没给时长时按 45 分钟算（不是独立景点的 120 分钟），同一天时路线上与所属景区紧挨着。
2026-10-30 南京实测：「钟山风景名胜区中山陵景区音乐台」按 120 分钟算，和中山陵一起放不下，被拆到第 2 天 07:00 单独打车去；
只改时长后又排成「音乐台 → 南博 → 中山陵」（住处按景点中心估算、离南博更近），等于出了景区再进一次。
所属景区也在同一天时，子景点**不占每日景点名额**（`calendar_pack.cap_spots`，分天穷举、启发式、空档补点同一口径；
两个互相包含的如「中山陵」「中山陵景区」都算）。第 4 轮测评凤凰：虹桥（08:00-17:00，夜游排不了）因第 1 天已有
沱江泛舟、凤凰古城、熊希龄故居 3 个而没排上，当天下午却空着 2 小时。

**指定日期**：用户说了某个景点哪天去（「第二天去长隆」），模型在 `spots` 里给它 `"day": N`，排程开始时换算成
`Spot.fixed_date`，其他日子一律按「去不了」处理——分天穷举、启发式、跨天对调、空档补点、校验器都沿用闭馆日的判定，
不另写一套。指定那天放不下或闭馆的进未安排并写明原因；超出行程天数直接报错。第 4 轮测评广州：用户说
「第二天把陈家祠换成长隆」，没有这个参数时长隆被排到第 1 天，模型回复却说「已替换」。

**当天顺序**：估算分钟数相差 ≤5 分钟的路线视为打平，选总公里数少的。步行段 13 分钟/km、打车段另加 5 分钟起步，
分钟数会把「多打两段车」和「走两段路」算成差不多：南京第 3 天「老门东 → 总统府 → 夫子庙」71 分钟 14.5km，
「总统府 → 老门东 → 夫子庙」72 分钟 9.4km，旧版选了前者。随机 300 例对比：8 例顺序改变，7 例变短，合计少走 47km，景点数不变。
例如南京 9 个点按均衡档（白天 420 分钟）放不下「老门东下午 + 夫子庙晚上」同一天，即使这项代价调到 5000 也只能拆开。

可行性判断：

- 通勤按直线估算 × 1.25：实测高德驾车耗时普遍比直线估算长约 30%，按估算刚好放得下的一天，排时间轴时会超时；
- 返程日按最后一站到车站的路程倒推可用时间；
- 夜游景点占晚餐后的窗口（约 175 分钟），不占白天预算；没标时段、但行程每天都要 17:00 后才开门的景点自动按夜游排；
- 每天**白天**景点数受节奏限制：轻松 2 个、均衡 3 个、紧凑 4 个；晚餐后的夜游另加 1 个，不占白天名额
  （旧版夜游占名额，南京实测第 3 天白天只排 2 个、下午空 2.5 小时）。空档补景点时按同一规则计数，
  但名额按时长折算（`scheduler.cap_load`：游玩 ≥90 分钟算 1 个，60 分钟约 0.67 个），只比分天时宽、不会更严。
  第 4 轮重庆：李子坝、解放碑、十八梯各 60 分钟就算满额，下午空 2.5 小时，备选的鹅岭公园没补进来；
  第 4、5 轮空档 ≥2 小时的 21 天里有 7 天属于这种情况。分天穷举仍按个数算：一天塞进 7、8 个短景点时全排列会爆。

穷举时车程按坐标缓存、只枚举满足「早 → 中 → 晚」的游览顺序、营业时间解析结果缓存，
12 个点 4 天（紧凑档）约 0.4 秒，含 3 个夜游与 2 家连锁店的最坏情况约 3.6 秒。
上限从 10 提到 12，是因为紧凑档 3 天补满正好 12 个：随机 11~12 个点的对比测试里，启发式平均少排 1.4 个点、
丢 1.4 个点名景点、每天多空约 50 分钟。超过 12 个才退回启发式。
启发式把挤出来的点放回有余量的天时，点名的放不回任何一天，就换掉某天一个没点名的
（随机 300 例两个种子：8 例少丢点名景点，没有变差的）。

### 出行人群与重排上限

- `mobility="limited"`（同行有老人、小孩或行动不便）：道路超过 1 公里改打车（平时 2 公里），节奏最多到均衡档，
  并在行程备注里写明。设置存在按会话缓存的 `PoiRepo.prefs` 里，后续轮次模型漏传时沿用，不靠模型每轮都记得；
  只在进程内存里，重启后由模型按对话历史重新传。
- 一轮回复最多成功生成 2 份行程（首次 + 按 gaps 补检索后重排一次），第 3 次调用直接拒绝、前端保留上一份。
  2026-10-30 测评里模型为放下一个景点重排了 6 次、耗时 3 分钟，只靠提示词约束不住。参数错误等失败的调用不计。

### 同品牌分店

用户只说了品牌（「先锋书店」）时，模型在该景点上加 `any_branch: true`。数据层按品牌名在同城检索
（只认「品牌(分店名)」形式且品牌一致的，最多 5 家），作为 `Spot.branches`；分天穷举时对每个组合
按「插进当天其他地点之间多走的距离」选最近的一家（逐家重排整天路线太慢：12 个点含 2 家连锁店要 12 秒），当天闭店的不选；
启发式分天时按每天的完整路线比（走得通优先、通勤最短，估算分钟打平时比总公里数）。
换了店的在行程里注明原选哪家。

实测南京：模型选了五台山总店，从玄武湖打车 4km 过去；玄武湖分店就在湖边。分店由确定性代码按路线选，不让模型凭印象挑。

### 大型景区门区

玄武湖、西湖、圆明园这类占地广的景区，高德给的 `location` 是几何中心，可能在湖心、山里或景区另一侧，
离实际进出的门区几公里。2026-10-29 实测：

| 景区 | 出发地 | 按中心点 | 按门区 |
|---|---|---|---|
| 玄武湖景区 | 湖南路 | 驾车 29 分钟 / 5.8km | 步行 20 分钟 / 1.3km，从「玄武门」进 |
| 圆明园遗址公园 | 北京大学东门 | 驾车 26 分钟 / 2.8km | 步行 21 分钟 / 1.2km，从「绮春园宫门」进 |
| 故宫博物院 | 王府井 | 驾车 35 分钟 / 4.2km | 步行 13 分钟 / 0.7km |
| 南京博物院（小型场馆） | 新街口 | 32 分钟 | 32 分钟（不受影响） |

门区来源（`app/_data/poi_repo.py`）：

- 检索结果自带的导航入口 `entr_location`（无名称，不额外请求）；
- 风景名胜类景点在生成行程时查一次 v5 `/place/detail?show_fields=children`，取 typecode `9914xx`（门）的子点，
  以及名称带「门」的景点售票处（`070306`，如圆明园「东门售票处」）。停车场、游客中心不算：有的停车场在园内。
  离中心超过 5km 的子点视为异常丢弃，相距 150m 内的合并（有名字的优先）。v5 查询失败时只用导航入口，不影响排程。

使用（`app/engine/geo.py`）：`Spot.gates` 非空时，两地之间一律按**最近的一对出入口**算（`gate_pair` / `place_distance`），
分天、挑餐厅、空档补景点、回住处判断、路网请求与校验器都用同一口径；进出可以是不同的门。
路段描述里写明从哪个门进出（如「步行约 5 分钟 (0.2 km)，从「解放门」进」），无名称的导航入口只修正坐标、不写进描述。

局限：只有导航入口、没有门区子点的景区（实测西湖、故宫、中山陵）只能按一个入口算。

**单向参观（进出口不同）**：`Spot.entry_points` / `exit_points`，由模型在 spots 里给 `entry_id` / `exit_id`
（用 `search_scenic_spots` 搜出的门 POI，如「故宫博物院-神武门」），`app/_data/trip_input.py` 换成坐标，查不到的写进说明、按普通入口算。
`gate_pair` 有方向：离开 a 用 a 的出口，到达 b 用 b 的入口；「是不是同一片区」用 `area_distance`（所有门、不分方向）。
出口只出不进，所以不能加进 `gates`，否则可能排成「先上景山、再从神武门进故宫」。第 4 轮测评北京 3 天景山和故宫被拆到两天：
高德给故宫的只有东侧导航入口，故宫—景山 1.07km；补上神武门出口后 0.15km，两者同一天、先故宫后景山（`tests/test_entry_exit.py`）。

### 时间轴

- **通勤**：写进时间轴的路段与校验都用高德路网；挑候选（哪家餐厅、哪个空档景点）只用估算，避免为每个候选请求一次。
- **餐厅**：按「绕路距离」挑选。离当前位置 ≤2.5km 或绕路 ≤1km 可选，绕路超过 4km 一律不选；
  路网距离 ≥ 直线 3 倍且多出 ≥2km 的（多半隔水，需轮渡或绕桥）不专程去；
  咖啡、茶饮、甜品、糕饼店不作正餐，人均超过 ¥60 的不进小吃档；用户没给预算时，人均超过 ¥150 的降权。
- **午餐**：下一个景点会拖过 13:30 时先吃午饭——只要此刻已过 10:30，就等到 11:30 开饭（中间的空档照常补景点或标出）。
  旧版要求 11:00 之后，南京实测 10:54 游完一处、下一处要 2.5 小时，午饭拖到 13:49。分天阶段的时间模拟用同一规则。
- **小吃**：只挑顺路的（比直接去当天终点多走 ≤1km），不为吃一口专程打车，也不在回住处休整后再出门；
  点名的必吃仍按 2.5km 半径挑。
- **两顿间隔**：上一顿吃完到下一顿开始至少 90 分钟（`MEAL_GAP_MIN`）。小吃排在午饭后 90 分钟起、最晚 16:20 开始
  （为此晚饭最多顺延到 18:30）；午饭吃得晚（游大景点到下午）时晚饭往后推；返程日告别餐提前后离午饭不足 90 分钟的，
  宁可省略并提示车站附近吃。第 4 轮测评 12 例有 17 处挨着吃（午饭 14:25 吃完 14:35 又排小吃、游长隆到 15:30
  吃午饭后 18:13 又吃晚饭）；随机 300 例 38 处降到 0，代价是小吃从 32 份减到 24 份、4 顿告别餐改为省略。
- **必吃**：绕路 ≤1km 时强制优先，返程日放宽到 2km、全程最后一顿 3km；早茶类不排晚餐；
  排不进的写入 `unmet_must_eat` 并说明原因。
- **时段**：宜早去的景点按开门时间提前出发；夜游放在晚餐后，放不下的改白天并提示；
  看日落的（模型给 `best_period="sunset"`，记为 `evening` + `Spot.sunset`，分天与夜游同等对待）排在晚饭前，
  游览时段尽量盖住 [日落 − 60 分钟, 日落 + 30 分钟]（游得短的晚些到），晚饭顺延到游完之后；日落前后放不下时按夜游再排。
  第 5、6 轮广州塔按夜游 19:25 上塔，当天 17:51 已日落，下午还空着 2.5 小时；改后 16:51–19:21（`tests/test_sunset.py`）。
  返程日按车次倒推，留出到站缓冲，告别餐最早可提前到 16:00。
- **空档**：空档 ≥60 分钟时，从「没排进的用户景点」和备选景点里挑一个顺路、营业中的补进去；太远时先回住处休整。
  户外景点只补到当地日落前（`geo.sunset_minutes`，按经纬度和日期算，误差几分钟）；博物馆、书店等室内场所
  （按高德分类与名称识别，`Spot.is_indoor`）不受限。南京实测 11 月底 16:38 补进明孝陵，17:05 天就黑了。
  代价是冬季下午能补的点变少：随机 300 例里天黑后才结束的户外补点从 11 个降到 0，同时少补了 12 个。
- **菜系去重**：同一菜系吃过后降权；高德分类笼统（「中餐厅」）时按店名认菜系（素食：素菜、素面、斋菜等；火锅：涮肉、涮羊肉）。
  去重跨天：全程吃过的菜系都降权。南京实测午餐百味斋素菜馆、晚餐鸡鸣寺素面馆，后者分类是「中餐厅」，旧版没认出是同一类；
  北京第 4 轮连续两天午餐都是铜锅涮肉，一家分类是「火锅店」、一家是「清真菜馆」（`tests/test_cross_day_cuisine.py`）。
- **掉点补救**：分天按估算放得下、排时间轴时按真实车程却放不下的景点，尝试与其他天的景点对调后整趟重排；
  只在「点名景点丢得更少」或「排进的总数更多」时采用，最多尝试 12 种。

## 数据源

| 来源 | 用途 | 结论 |
|---|---|---|
| 高德 `/v3/place/text`、`around` + `extensions=all` | 地点、评分、人均、营业时间 | **主力数据源**；不传 `extensions=all` 就没有评分与营业时间 |
| 高德 `/v3/weather/weatherInfo` | 天气预报 | 参数要 adcode，不是城市名 |
| 高德 `/v3/distance` | 步行 / 驾车路网时长与距离 | 排程通勤的数据来源 |
| 维基百科系 | — | 国内网络不可达，不可用 |
| 大众点评 / 美团 | — | 没有公开 API |

高德使用要点（均为实测）：

- 关键词检索必须带 `citylimit=true`，否则 city=南京 搜「西湖」返回的是杭州；
- 没有「小吃」分类码：`050400` 实际是茶饮咖啡、`050900` 是甜品，地方小吃都在 `050100 中餐厅` 下，
  因此用关键词检索再按 `type` 字段二次过滤；
- 周边检索是严格匹配，名称错一个字就返回 0 条。

景点背景介绍交给模型自身知识，外部接口只提供实时信息（营业时间、距离、评分、天气）。

更详细的接口调研见 [API-RESEARCH.md](API-RESEARCH.md)。

## 前端 `src/`

React 18 + Vite，接口调用集中在 `src/api.ts`。生产环境由后端托管 `dist/`，开发时 Vite 把接口代理到后端。主要组件：

| 组件 | 作用 |
|---|---|
| `App.tsx` | 布局、SSE 消费、会话状态 |
| `ChatWindow` / `ChatBubble` | 消息列表，Markdown 渲染（不启用原始 HTML） |
| `TripPlanCard` | 行程卡片：按天切换的时间线，展示通勤、营业时间、价格、提示，以及每餐满足的必吃 |
| `ToolIndicators` | 五个工具的实时指示灯 |
| `ConversationSidebar` | 会话列表（数据来自 `/conversations`） |
| `DebugPanel` / `CodeViewer` | 调试面板 |

界面支持中英切换（`src/i18n/`），≤640px 宽度时切换为手机布局。行程卡片内容由引擎生成，固定为中文。
